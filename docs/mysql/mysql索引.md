## 什么是索引

索引(index)是帮助 MySQL **高效获取数据**的**数据结构**(有序)。在数据之外,数据库系统还维护着满足特定查找算法的数据结构,这些数据结构以某种方式指向数据,这样就可以在这些数据结构上实现高级查找算法。

可以把它类比成一本书的**目录**:想找某一章,不用从第一页翻到最后一页,先查目录,再直接翻到对应页码。

没有索引时,MySQL 只能把整张表从头到尾扫一遍(**全表扫描**);有了索引,就能快速定位到需要的数据。

| | 优势 | 劣势 |
| --- | --- | --- |
| 查询 | 提高数据检索效率,降低数据库的 I/O 成本 | |
| 排序 | 通过索引列对数据排序,降低排序成本,降低 CPU 消耗 | |
| 空间 | | 索引本身也是数据,要占用磁盘空间 |
| 增删改 | | 索引大大提高了查询效率,同时也降低了更新表的速度(插入、修改、删除时,索引也要一起维护) |

::: tip 示例表
本文的 SQL 例子基于一张用户表(下文的动画使用的是它的简化版):

```sql
create table tb_user (
  id         int primary key auto_increment comment '主键',
  name       varchar(50) not null comment '姓名',
  phone      varchar(11) not null comment '手机号',
  email      varchar(100) comment '邮箱',
  profession varchar(50) comment '专业',
  age        int comment '年龄',
  gender     char(1) comment '性别',
  status     char(1) comment '状态',
  createtime datetime comment '创建时间'
) comment '用户表';
```
:::

## 索引的数据结构

MySQL 的索引是在**存储引擎层**实现的,不同的存储引擎有不同的索引结构,主要包含以下几种:

| 结构 | 描述 |
| --- | --- |
| B+Tree 索引 | 最常见的索引类型,大部分引擎(包括 InnoDB)都支持 |
| Hash 索引 | 底层用哈希表实现,只有精确匹配的查询才有效,**不支持范围查询**;Memory 引擎支持(InnoDB 里有"自适应哈希索引",由引擎自动管理,不能手动创建) |
| R-tree(空间索引) | MyISAM 引擎的一个特殊索引类型,主要用于地理空间数据,使用较少 |
| Full-text(全文索引) | 通过建立倒排索引,快速匹配文档,类似 Lucene、ES |

我们平时说的"索引",如果没有特别说明,指的都是 **B+Tree 索引**。

### 为什么是 B+Tree

假设用二叉树存储索引:数据按顺序插入时会退化成一条链表,查找接近全表扫描;即使是红黑树这样自平衡的二叉树,每个节点也只有两个孩子,数据量大时**树的层数会很深**。而数据库的索引存在磁盘上,**每多读一层就多一次磁盘 I/O**,层数越深越慢。

所以需要一种**"矮胖"**的多叉树。B-Tree 和 B+Tree 都是多路平衡树,InnoDB 选择了 B+Tree,它在 B-Tree 的基础上做了两个关键改进:

| 对比 | B-Tree | B+Tree |
| --- | --- | --- |
| 数据存放位置 | 所有节点(包括非叶子节点)都存数据 | **只有叶子节点**存数据,非叶子节点只存键和指针 |
| 一页能放多少键 | 非叶子节点也要存数据,放得少,树更高 | 非叶子节点只存键,放得多,树更矮 |
| 叶子节点之间 | 没有联系 | 通过**双向链表**相连,范围查询、排序更方便 |
| 查询效率 | 不稳定(可能在中途节点命中) | 稳定,每次都要走到叶子 |

InnoDB 的每个节点是一个**页**,默认大小 16KB。我们来估算一下:

- 非叶子节点:假设主键是 `bigint`(8 字节),再加上指针(约 6 字节),每个键值约 14 字节,一页大约能放 16 × 1024 / 14 ≈ **1170** 个指针。
- 叶子节点:假设一行数据约 1KB,一页大约能放 **16** 行。
- 树高为 3 层时,能存的行数约为 1170 × 1170 × 16 ≈ **2190 万**。

也就是说,**两千多万行的表,通过主键找一行数据,只需要读 3 个页**。

### B+Tree 的存储结构

上面提到"节点就是页",下面把这件事彻底讲清楚:数据在磁盘上到底是怎么存的,一棵 B+Tree 又是怎么一步步"长"出来的。

#### 页:磁盘与内存交互的基本单位

磁盘读写很慢,所以 InnoDB 不会一条一条地读写记录,而是以**页(Page)**为最小单位:不管你只想读 1 行还是 10 行,都要把包含它的那一整页(默认 16KB)读进内存。页是 InnoDB 磁盘管理的最小单位,也是 B+Tree 的节点。

InnoDB 的存储空间由大到小分成这几层:

| 层级 | 说明 |
| --- | --- |
| 表空间(Tablespace) | 最大的逻辑容器,一个表(开启 `innodb_file_per_table` 时)对应一个 `.ibd` 文件 |
| 段(Segment) | 每个索引有两个段:**叶子节点段**和**非叶子节点段**,分别管理叶子页和非叶子页 |
| 区(Extent) | 空间分配的基本单位,大小固定为 1MB,包含 64 个连续的页(64 × 16KB) |
| 页(Page) | 磁盘管理的最小单位,默认 16KB,**B+Tree 的一个节点就是一个页** |
| 行(Row) | 真正存放数据的记录 |

#### 页的内部结构

一个 16KB 的页并不是把行数据一股脑塞进去,而是分成几个固定的部分:

| 组成 | 大小 | 作用 |
| --- | --- | --- |
| File Header(文件头) | 38 字节 | 页号、**上一页页号、下一页页号**(正是靠它们把同一层的页串成**双向链表**)、页类型等 |
| Page Header(页头) | 56 字节 | 本页的记录数、槽数、空闲空间位置等状态信息 |
| Infimum + Supremum | 26 字节 | 两条虚拟记录:**最小记录**和**最大记录**,分别当作页内记录链表的头和尾 |
| User Records(用户记录) | 不固定 | 真正存放的数据,按主键从小到大用 **next_record 指针串成单向链表** |
| Free Space(空闲空间) | 不固定 | 还没用到的空间,插入新记录时从这里分配;用完了就要新开页 |
| Page Directory(页目录) | 不固定 | 一组**槽(slot)**,每个槽指向一组记录里最大的那一条,用来**二分查找** |
| File Trailer(文件尾) | 8 字节 | 校验和,用来检查页是否完整地写入了磁盘 |

页里的记录是单向链表,按理说查找只能从头一条条比较。为了加快页内查找,InnoDB 把记录分成若干组(每组大约 4~8 条),每组的**最大记录**在页目录里占一个槽。查找时**先对槽做二分查找**,锁定到某一组,再沿着链表在这一小组里顺序比较。

#### 叶子页和非叶子页里放的是什么

页的结构是一样的,区别只在"用户记录"部分存了什么:

| 页类型 | 每条记录里存的内容 | 说明 |
| --- | --- | --- |
| 非叶子页(索引页) | **键值 + 指向子页的页号** | 不存行数据,所以一页能放很多条,树才能"矮胖" |
| 叶子页(数据页)·聚集索引 | **键值 + 整行数据** | 一页能放的行数取决于行的大小 |
| 叶子页(数据页)·二级索引 | **索引列的值 + 主键值** | 记录很小,一页能放得更多 |

#### B+Tree 是怎么"长"出来的

B+Tree 是在不断插入数据的过程中**自己长大**的:新数据放进叶子页,页满了就**分裂**成两个页,并在父节点里记一笔;如果父节点也满了,继续向上分裂;一直分裂到根节点时,就产生新的根节点,**树长高一层**。

为了方便观察,下面的动画把每个节点的容量设成**最多 3 个键**(真实的页能放几百上千个)。

**1. 按顺序插入**(类似自增主键):依次插入 1 ~ 12。观察每一步:找到叶子 → 放入 → 溢出 → 分裂 → 向上传递 → 根节点分裂、树长高。

<BPlusBuildDemo mode="ordered" />

注意分裂时两种节点的区别:

| 分裂的节点 | 中间的分界键怎么处理 |
| --- | --- |
| **叶子节点** | 新页的第一个键被**复制**一份到父节点,叶子里**仍然保留**它(因为数据只存在叶子里,不能丢) |
| **内部节点** | 中间的键**上移**到父节点,内部节点里**不再保留**它(内部节点本来就只是"路标") |

**2. 乱序插入**(类似 UUID 这种随机主键):同样是这 12 个数,换成乱序。

<BPlusBuildDemo mode="random" />

对比两种插入方式就能理解前面"主键设计建议"的由来:

- **有序插入**:新键永远追加到最右边的叶子,只有最右边的页满了才分裂,前面已经写满的页不会再被改动,磁盘写入是**顺序**的。
- **乱序插入**:新键会落到树里任意位置的页,哪个页满了就分裂哪个,数据要在页之间来回搬移,容易产生**页碎片**,磁盘写入变成**随机**的,性能明显更差。

::: tip 关于动画的简化
为了便于观察,动画里的分裂始终是"一分为二"。真实的 InnoDB 做了更多优化,比如检测到是**顺序插入**时,分裂不会把页对半分,而是只新开一个页,让前面的页尽量写满(可以达到约 15/16 的填充率)。所以实际的有序插入比动画里看起来更省空间。
:::

#### 叶子之间的双向链表

注意到动画里叶子节点之间的 ⇄ 了吗?每个叶子页的 File Header 里都记录着**上一页和下一页**的页号,所有叶子页因此串成了一个**有序的双向链表**。

这个设计让 B+Tree 特别适合范围查询、排序:定位到起点之后,不需要再回到根节点,直接**沿着链表往后读**就可以了(见下面的范围查询动画)。

## 索引分类

### 按功能分类

| 分类 | 含义 | 特点 | 关键字 |
| --- | --- | --- | --- |
| 主键索引 | 针对表中**主键**创建的索引 | 默认自动创建,**只能有一个** | `PRIMARY` |
| 唯一索引 | 避免同一个表中某数据列中的值重复 | 可以有多个 | `UNIQUE` |
| 常规索引 | 快速定位特定数据 | 可以有多个 | |
| 全文索引 | 全文索引查找的是文本中的关键词,而不是比较索引中的值 | 可以有多个 | `FULLTEXT` |

### 按存储形式分类(InnoDB)

在 InnoDB 存储引擎中,根据索引的存储形式,又可以分为两种:**聚集索引**和**二级索引**。

| 分类 | 含义 | 特点 |
| --- | --- | --- |
| 聚集索引(Clustered Index) | 将**数据存储与索引放到了一块**,索引结构的叶子节点保存了**行数据** | **必须有,而且只有一个** |
| 二级索引(Secondary Index) | 将**数据与索引分开存储**,索引结构的叶子节点关联的是对应的**主键** | 可以存在**多个** |

#### 聚集索引

聚集索引就是一棵 B+Tree,它的特殊之处在于**叶子节点存放的就是完整的行数据**。换句话说,**表本身就是按聚集索引组织起来的**(这也是 InnoDB 的表被称为"索引组织表"的原因)。上面 B+Tree 动画里的那棵树,就是一棵聚集索引。

每张表只有一份数据,所以聚集索引**有且只有一个**。InnoDB 按下面的规则选取聚集索引:

1. 如果表**有主键**,主键索引就是聚集索引;
2. 如果表**没有主键**,就使用**第一个唯一(`UNIQUE`)且非空**的索引作为聚集索引;
3. 如果以上都没有,InnoDB 会**自动生成一个隐藏的 `rowid`**(6 字节)作为隐藏的聚集索引。

#### 二级索引

除了聚集索引之外,为其他字段创建的索引(常规索引、唯一索引等)都是**二级索引**,也叫**辅助索引**。

二级索引也是一棵 B+Tree,它的叶子节点**不存整行数据**,只存**索引列的值 + 对应行的主键值**。一张表可以有多个二级索引,每个二级索引都是一棵独立的 B+Tree。

比如给 `name` 字段创建一个二级索引:

```sql
create index idx_name on tb_user(name);
```

它的叶子节点存的是 `(name, id)`,按 `name` 排序。

#### 回表查询

既然二级索引的叶子节点只有主键值,那么通过二级索引查数据就有两种情况:

- **需要的字段,二级索引里都有** → 直接返回,不用再去查别的。
- **需要的字段,二级索引里没有** → 先通过二级索引查到**主键值**,再拿着主键值回到**聚集索引**中查出整行数据。这个过程叫**回表查询**。

查询所用到的字段在一个索引里就能全部拿到(查询列被索引"覆盖"),不用回表。回表意味着多查一棵 B+Tree,所以应该**尽量使用覆盖索引,避免 `select *`**。
:::

#### 由此带来的主键设计建议

因为聚集索引决定了数据的物理组织方式,而每个二级索引的叶子节点里都存着主键值,所以:

| 建议 | 原因 |
| --- | --- |
| 主键**尽量短**(`int`、`bigint`,不要用很长的字符串) | 每个二级索引的叶子节点都要存一份主键值,主键越长,所有二级索引越占空间 |
| 主键**尽量单调递增**(如 `auto_increment`) | 数据总是追加在 B+Tree 的末尾,页写满了再开新页;如果主键是随机的(如 UUID),新数据要插到中间的页,页满了会发生**页分裂**,产生大量碎片,性能变差 |
| 不要用经常修改的字段做主键 | 主键变了,聚集索引里的数据要移动位置,所有二级索引也要同步修改 |

## 索引语法

```sql
-- 创建索引(unique、fulltext 可选;一个索引可以关联多个字段,即联合索引)
create [unique | fulltext] index 索引名 on 表名 (字段名, ...);

-- 查看某张表的索引
show index from 表名;

-- 删除索引
drop index 索引名 on 表名;
```

```sql
-- name 字段可能重复,创建常规索引
create index idx_user_name on tb_user(name);

-- phone 字段值唯一且非空,创建唯一索引
create unique index idx_user_phone on tb_user(phone);

-- 为 profession、age、status 创建联合索引
create index idx_user_pro_age_sta on tb_user(profession, age, status);

-- 为 email 创建索引
create index idx_user_email on tb_user(email);
```

::: tip 自动创建的索引
- 建表时指定的**主键**,会自动创建主键索引(也就是聚集索引)。
- 声明 `unique` 约束的字段,会自动创建唯一索引。
:::

## 性能分析:explain

怎么知道一条 SQL 有没有用上索引?用 `explain`(或 `desc`)查看它的**执行计划**:

```sql
explain select * from tb_user where id = 1;
```

| 字段 | 含义 |
| --- | --- |
| `id` | select 查询的序列号,表示查询中执行 select 子句或操作表的顺序(id 相同,从上往下执行;id 不同,值越大越先执行) |
| `select_type` | 查询类型,常见:`SIMPLE`(简单表,没有表连接或子查询)、`PRIMARY`(主查询)、`SUBQUERY`(子查询)、`UNION` 等 |
| `table` | 表名 |
| `type` | **连接类型**,性能从好到差:`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。`ALL` 就是全表扫描,`index` 是全索引扫描 |
| `possible_keys` | 可能用到的索引 |
| `key` | **实际用到的索引**,为 `NULL` 表示没用索引 |
| `key_len` | 使用到的索引的**最大长度**(字节),在不损失精度的前提下越短越好;联合索引时可以据此判断用到了几列 |
| `rows` | MySQL 认为必须要执行查询的行数(估算值) |
| `filtered` | 返回结果的行数占需要读取行数的百分比,越大越好 |
| `Extra` | 额外信息,见下表 |

`type` 的几个典型取值:

| type | 出现的场景 |
| --- | --- |
| `const` | 通过**主键或唯一索引**做等值查询 |
| `ref` | 使用**非唯一索引**做等值查询 |
| `range` | 索引范围查询(`between`、`>`、`in` 等) |
| `index` | 遍历了整个索引树(比全表扫描快一点,因为索引通常比数据小) |
| `ALL` | **全表扫描**,要特别警惕 |

`Extra` 的常见取值:

| Extra | 含义 |
| --- | --- |
| `Using index` | 使用了**覆盖索引**,不需要回表 |
| `Using where` | 使用了 where 条件过滤。如果没有 `Using index`,说明需要回表后再过滤 |
| `Using index condition` | 使用了索引,但是需要回表查询数据(索引下推 ICP 的情况) |
| `Using filesort` | 排序没能利用索引,需要在内存或磁盘里额外排序,**通常需要优化** |
| `Using temporary` | 用到了临时表,常见于 `group by`、`distinct`,**通常需要优化** |

## 索引的使用规则

### 最左前缀法则

如果索引了**多列**(联合索引),要遵守最左前缀法则:**查询从索引的最左列开始,并且不跳过索引中的列**。如果跳跃了某一列,索引将部分失效(后面的字段索引失效)。

以联合索引 `(profession, age, status)` 为例,它在 B+Tree 里是先按 `profession` 排序,`profession` 相同再按 `age` 排序,`age` 也相同再按 `status` 排序。如果跳过了 `profession`,`age` 在整棵树里就不是有序的了,自然没法用来定位。

| where 条件 | 能用到的列 |
| --- | --- |
| `profession = ? and age = ? and status = ?` | 3 列都能用 |
| `profession = ? and age = ?` | `profession`、`age` |
| `profession = ?` | `profession` |
| `age = ? and status = ?`(缺少最左列) | **索引失效** |
| `profession = ? and status = ?`(跳过了 `age`) | 只用到 `profession`,`status` 用不上 |
| `status = ? and age = ? and profession = ?`(顺序颠倒) | 3 列都能用(只要这些列**出现**即可,与书写顺序无关,优化器会调整) |

### 范围查询

联合索引中,出现**范围查询**(`>`、`<`)时,**范围查询右侧的列无法再用来缩小索引的查找范围**。

```sql
-- age 用了 >,status 用不上索引来定位
select * from tb_user where profession = '软件工程' and age > 30 and status = '0';

-- 范围条件尽量用 >=、<=、between,右侧的列仍然可以继续使用
select * from tb_user where profession = '软件工程' and age >= 30 and status = '0';
```

::: tip 以 explain 为准
`>=` 能让右侧的列继续生效,是因为"从 (软件工程, 30, 0) 开始往后扫"这个起点是可以精确定位的。具体用到几列,以 `explain` 的 `key_len` 为准。能用 `>=`、`<=` 表达的,业务允许的话尽量用它们。
:::

### 索引列上不要做运算

在索引列上进行**运算**(函数、表达式),索引会失效:

```sql
-- ❌ 对 phone 使用了函数,索引失效,变成全表扫描
select * from tb_user where substring(phone, 10, 2) = '15';

-- ✅ 尽量把运算放到等号右边的常量上
select * from tb_user where age = 30 + 1;
```

### 字符串不加引号

字符串类型的字段使用时,**不加引号**会发生隐式类型转换,导致索引失效:

```sql
-- ✅ 走索引
select * from tb_user where phone = '17799990015';

-- ❌ phone 是 varchar,这里数字会触发类型转换,索引失效
select * from tb_user where phone = 17799990015;
```

### 模糊查询

如果是**尾部模糊匹配**,索引不会失效;如果是**头部模糊匹配**,索引失效(因为 B+Tree 是按字符串从左到右排序的,头部不确定就没法定位)。

```sql
select * from tb_user where profession like '软件%';   -- ✅ 走索引
select * from tb_user where profession like '%工程';   -- ❌ 失效
select * from tb_user where profession like '%工%';    -- ❌ 失效
```

### or 连接的条件

用 `or` 分割开的条件,**只有当 or 两侧的字段都有索引时才会用上索引**,只要有一侧没有索引,涉及的索引都不会被用到:

```sql
-- id 有索引,age 没有索引 → 整条 SQL 不会用索引(退化成全表扫描)
select * from tb_user where id = 10 or age = 23;

-- 给 age 也建上索引之后,两侧都有索引,才会用到
create index idx_user_age on tb_user(age);
```

### 数据分布的影响

如果 MySQL 评估使用索引比全表扫描还慢,就**不会使用索引**。比如某个值在表里占了绝大部分行,用索引需要大量回表,还不如直接顺序扫描整张表。这取决于数据的分布情况,同一条 SQL 在不同的数据下可能有不同的执行计划。

### SQL 提示

在优化器选错索引时,可以人为地给它一个提示:

```sql
-- 建议使用某个索引(优化器可以忽略)
select * from tb_user use index(idx_user_pro) where profession = '软件工程';

-- 忽略某个索引
select * from tb_user ignore index(idx_user_pro) where profession = '软件工程';

-- 强制使用某个索引
select * from tb_user force index(idx_user_pro) where profession = '软件工程';
```

### 覆盖索引与 select *

前面讲过,覆盖索引就是查询的字段在索引里都能拿到,不需要回表。所以:

```sql
-- ✅ 只查联合索引 (profession, age, status) 里有的列(外加主键),可以覆盖,Extra 显示 Using index
select id, profession, age, status from tb_user where profession = '软件工程' and age = 31;

-- ❌ select * 通常需要回表,Extra 显示 Using index condition 或 Using where
select * from tb_user where profession = '软件工程' and age = 31;
```

::: warning 尽量避免 select *
`select *` 几乎一定要回表,而且会读取很多用不上的列。只查需要的字段,有机会走覆盖索引。
:::

### 前缀索引

当字段是字符串(`varchar`、`text` 等)且很长时,把整个字符串建成索引会占用大量空间,查询时也浪费 I/O。可以只取字符串的**前几个字符**建索引,这就是**前缀索引**:

```sql
create index idx_xxx on 表名(字段名(n));
```

前缀长度 n 取多少合适?取决于**选择性**:不重复的索引值(基数)与总记录数的比值,**越接近 1,区分度越高,查询效率越高**。

```sql
-- 整个字段的选择性
select count(distinct email) / count(*) from tb_user;

-- 取前 5 个字符的选择性,与上面对比,差不多就够用了
select count(distinct substring(email, 1, 5)) / count(*) from tb_user;

-- 创建前缀长度为 5 的索引
create index idx_email_5 on tb_user(email(5));
```

前缀索引是用"区分度的少许损失"换"空间的节省",但它**不能当覆盖索引使用**(因为索引里只有前缀,没法直接取完整的值)。

### 单列索引与联合索引

- **单列索引**:一个索引只包含单个列。
- **联合索引**:一个索引包含多个列。

当一条 SQL 的 where 条件涉及**多个字段**时,**优先建联合索引**。如果建的是多个单列索引,MySQL 通常只会选择其中一个(区分度最高的)来用,其余条件还是要回表后再过滤;而一个联合索引能同时利用多个条件,还有机会形成覆盖索引。

```sql
-- 例如经常这样查
select id, phone, name from tb_user where phone = '17799990010' and name = '韩信';

-- 建联合索引:查询时先用 phone 定位,name 在索引里就能过滤,还可能覆盖 id、phone、name
create unique index idx_user_phone_name on tb_user(phone, name);
```

## 索引设计原则

1. **数据量较大**(比如超过百万),且查询比较频繁的表建立索引。小表没必要,全表扫描可能更快。
2. 针对于经常作为 **`where`、`order by`、`group by`** 操作条件的字段建立索引。
3. 尽量选择**区分度高**的列作为索引,尽量建立**唯一索引**。区分度越高,使用索引的效率越高。像"性别"这种只有两三个取值的字段,建索引基本没有意义。
4. 如果是**字符串类型**的字段,字段长度较长,可以针对字段的特点,建立**前缀索引**。
5. 尽量使用**联合索引**,减少单列索引。查询时,联合索引很多时候可以**覆盖索引**,节省存储空间,避免回表,提高查询效率。
6. **要控制索引的数量**。索引并不是多多益善,索引越多,维护索引结构的代价也就越大,会影响增删改的效率。
7. 如果索引列**不能存储 `NULL` 值**,请在创建表时使用 `NOT NULL` 约束。当优化器知道每列是否包含 `NULL` 值时,它可以更好地确定哪个索引最有效地用于查询。

## 小结

| 知识点 | 要点 |
| --- | --- |
| 索引 | 帮助 MySQL 高效获取数据的有序数据结构;提高查询效率,降低增删改效率,占用空间 |
| B+Tree | 非叶子节点只存键,叶子节点存数据并用双向链表相连;树矮(三层可存两千多万行),范围查询方便 |
| 聚集索引 | 叶子节点存**整行数据**,每张表**有且只有一个**(主键 → 第一个唯一非空索引 → 隐藏 rowid) |
| 二级索引 | 叶子节点存**索引列 + 主键值**,可以有多个 |
| 回表查询 | 通过二级索引拿到主键,再回聚集索引取整行;多查一棵 B+Tree |
| 覆盖索引 | 查询的列在索引里就能拿全,不用回表;避免 `select *` |
| 主键设计 | 短、单调递增、不常修改 |
| explain | 重点看 `type`(避免 `ALL`)、`key`、`key_len`、`Extra` |
| 使用规则 | 最左前缀、范围查询右侧失效、列上不运算、字符串加引号、头部模糊失效、or 两侧都要有索引 |
| 设计原则 | 大表、常用于 where/order by/group by、区分度高、优先联合索引、控制数量 |
